## 第一部分 接口说明

> 基址示例：`http://127.0.0.1:18080`
> 命名与协作约定见 《物小助开发规范》（第二部分）。
> 已实现：认证、单位信息、商品分类、商品、供应商、库存出入库、采购单与单级审批、收货入库（自动生成应付）、
> 应付账款与付款、补货参数与计算、首页预警与趋势、Excel 导出、采购单 PDF。
> AI 助手需接入真实模型服务（readme 问题 005），尚未实现。

### 1. 通用约定

| 项 | 约定 |
| --- | --- |
| 鉴权头 | `Authorization: Bearer <token>`；文件下载可用 `?token=` |
| 内容类型 | `application/json; charset=utf-8`（写接口） |
| 成功响应 | `{ "code": 200, "msg": "操作成功", ... }` |
| 分页响应 | `{ "code": 200, "rows": [...], "total": 12 }` |
| 分页参数 | `pageNum`（默认 1）、`pageSize`（默认 10，最大 100） |
| 未登录 | `{ "code": 401, "msg": "登录状态已过期，请重新登录" }` |
| 无权限 | `{ "code": 403, "msg": "没有操作权限：xxx" }` |
| 业务失败 | `{ "code": 500, "msg": "具体原因" }` |
| 单位隔离 | 单位 ID 只取自令牌，请求体中出现的 enterpriseId 一律忽略 |

### 2. 认证

#### 2.1 图形验证码

```
GET /captchaImage?type=math
```

`type`：`math`（默认，算术）/ `char`（字符）。

```json
{ "code": 200, "uuid": "1f3c...", "img": "/9j/4AAQSkZJRg..." }
```

`img` 为 Base64 JPEG，前端拼 `data:image/jpeg;base64,` 后展示；`uuid` 2 分钟内有效，校验后即失效。

#### 2.2 登录

```
POST /login
Content-Type: application/x-www-form-urlencoded

username=admin&password=admin123&code=12&uuid=1f3c...
```

验证码关闭时可省略 `code`、`uuid`。

```json
{ "code": 200, "msg": "登录成功", "token": "OaSJuyvRyMVG421QWkHutwNdy23YsjtibYs5hDXFSYU" }
```

失败：`{"code":500,"msg":"验证码错误"}` / `{"code":500,"msg":"用户或密码错误"}`。

#### 2.3 当前用户

```
GET /getInfo
Authorization: Bearer <token>
```

```json
{
  "code": 200,
  "user": { "userId": 1, "userName": "admin", "nickName": "若依", "deptId": 103, "avatar": "", "email": "ry@163.com", "phonenumber": "15888888888", "loginDate": "2026-11-05 10:57:15" },
  "roles": ["admin"],
  "permissions": ["*:*:*"]
}
```

#### 2.4 退出

```
POST /logout
Authorization: Bearer <token>
```

```json
{ "code": 200, "msg": "退出成功" }
```

令牌立即失效。后台 Web 仍可用 `GET /logout` 清会话后跳转登录页。

### 8. 采购单与审批

状态：`0 草稿 / 1 待审批 / 2 已通过 / 3 已驳回 / 4 已完成 / 5 已取消`

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/business/purchase/list` | 登录 | 分页；`status`、`keyword`（单号/供应商） |
| GET | `/business/purchase/todo` | 登录 | 待审批列表（status=1） |
| GET | `/business/purchase/{orderId}` | 登录 | 详情：单据 + 明细 + 审批记录 |
| POST | `/business/purchase` | `business:purchase:edit` | 新建草稿 |
| PUT | `/business/purchase/{orderId}` | `business:purchase:edit` | 编辑（仅草稿/已驳回） |
| POST | `/business/purchase/{orderId}/submit` | `business:purchase:edit` | 提交审批 |
| POST | `/business/purchase/{orderId}/approve` | `business:purchase:approve` | 通过，body 可带 `opinion` |
| POST | `/business/purchase/{orderId}/reject` | `business:purchase:approve` | 驳回，`opinion` 必填 |
| POST | `/business/purchase/{orderId}/cancel` | `business:purchase:edit` | 取消，`reason` 必填 |
| POST | `/business/purchase/{orderId}/receive` | `business:stock:edit` | 收货入库，body 可带 `remark` |

创建请求：

```json
{
  "supplierId": 1,
  "remark": "十月办公用品采购",
  "items": [
    { "productId": 1, "qty": 50, "price": 20 },
    { "productId": 2, "qty": 10, "price": 35.5 }
  ]
}
```

服务端按商品档案补全名称、规格、单位，金额 = 数量 × 单价，总额自动汇总；`supplierId` 必须为启用供应商。

业务联动：

- 提交：状态 0/3 → 1，版本号 +1；
- 通过：状态 1 → 2，写审批记录，按明细累加库存**在途量**；
- 驳回：状态 1 → 3，审批意见必填，可编辑后重新提交（版本继续递增）；
- 取消：状态 1/2 → 5，已通过的单据取消时冲减在途量；
- 收货：状态 2 → 4，生成收货单与入库流水（`sourceNo` = 采购单号），冲减在途、增加库存，并按订单金额与供应商账期生成应付账款；
- 管理员（userId=1）可代审并留痕，其他审批人不得审批自己创建的单据。

### 10. 补货

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/business/replenish/param/{productId}` | 登录 | 读取参数，无记录时返回默认值（周期 7 天、交期 3 天、系数 1.00） |
| PUT | `/business/replenish/param/{productId}` | `business:replenish:edit` | 保存参数（季节系数 0.80–1.50） |
| GET | `/business/replenish/suggestions` | 登录 | 分页；`status`、`keyword` |
| POST | `/business/replenish/calc` | `business:replenish:edit` | 手动触发计算，返回生成条数 |
| POST | `/business/replenish/suggestion/{id}/to-purchase` | `business:purchase:edit` | 建议转采购草稿，返回 `orderId`；商品需有默认供应商 |
| PUT | `/business/replenish/suggestion/{id}/status?status=2` | `business:replenish:edit` | 忽略建议（仅支持 2） |

参数请求：

```json
{ "safetyStock": 20, "maxStock": 200, "cycleDays": 7, "leadDays": 3, "seasonCoef": 1.2, "enableFlag": "1" }
```

计算口径：

```
d = 近 30 天出库量 / 30
G = max(安全库存, d × (周期 + 交期) × 季节系数)
Q = ceil(G − 可用库存 − 在途采购量)
Q = min(Q, 最大库存 − 可用库存 − 在途采购量)
Q ≤ 0 时不生成建议
```

定时任务每天 02:00 遍历启用单位执行（`cangxiaozhu.task.replenish-cron` 可改）。

### 14. 联调示例

```bash
# 登录
TOKEN=$(curl -s -X POST http://127.0.0.1:18080/login \
  -d "username=admin&password=admin123" | sed 's/.*"token":"\([^"]*\)".*/\1/')

# 新增分类
curl -X POST http://127.0.0.1:18080/business/category \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"办公用品","sort":1}'

# 入库
curl -X POST http://127.0.0.1:18080/business/stock/inbound \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"productId":1,"qty":100,"bizType":"其他入库"}'
```

> Windows 命令行直接拼中文 JSON 容易因 GBK 编码被服务端拒绝（`JSON parse error: Invalid UTF-8`），建议把请求体写入 UTF-8 文件后用 `--data-binary @file` 发送。

### 17. 智能检索

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/business/search/product?q=找到一台电脑的配套螺丝&limit=10` | 登录 | 自然语言/关键词检索商品，按相关度排序 |

返回：

```json
{
  "code": 200,
  "total": 1,
  "query": "找到一台电脑的配套螺丝",
  "rows": [
    { "productId": 3, "productCode": "P003", "productName": "笔记本专用螺丝 M2×5",
      "spec": "M2×5 不锈钢", "unit": "包", "stockQty": 0, "score": 1.0,
      "matchedTerms": ["笔记本", "螺丝"] }
  ]
}
```

匹配规则：

1. 先去掉"的、一台、帮我、配套"等口语词；
2. 把问题拆成概念，每个概念带近义词（电脑→计算机/笔记本/PC/台式机，螺丝→螺钉/螺栓/紧固件）；
3. 商品命中任一近义词即算命中该概念，名称权重 3、规格/编码 2、分类/备注 1；
4. `score = 命中权重 / (概念数 × 3)`，`matchedTerms` 给出命中的词，方便前端解释"为什么是这条"。

能力边界：这是**词法 + 同义词**匹配，可解释、无外部依赖，但无法理解"配套/兼容/可替代"这类语义关系。
真正的语义检索需要 Embedding 模型与向量库，接入方式见 `企划书` 第 6.7 节；届时本接口改为
"先向量召回、再走同一套打分兜底"，前端无需改动。


### 18. 幂等与审计

#### 18.1 幂等

- 所有写接口（POST/PUT/DELETE）必须带 `X-Request-Id`（建议 UUID）；
- 服务端以 `(enterprise_id, request_id)` 唯一键占位：首次执行、重复拦截；
- 缺失幂等键返回 500，重复提交返回 409；
- 上次执行失败时，允许用同一 `requestId` 重试（记录状态会回到处理中）；
- 记录保留 7 天，每天 03:30 清理，`cangxiaozhu.task.idem-clean-cron` 可调；
- `cangxiaozhu.idempotent.enabled=false` 可临时关闭，不建议用于生产。

#### 18.2 审计

`/business/**` 下所有非查询请求自动写入若依 `sys_oper_log`：

| 字段 | 内容 |
| --- | --- |
| `oper_name` | 当前登录账号 |
| `title` / `oper_url` | 请求路径 |
| `request_method` | POST / PUT / DELETE |
| `operator_type` | 2（移动端） |
| `status` | 0 成功 / 1 失败（按业务 code 判定） |
| `error_msg` | 失败原因 |
| `json_result` | 响应 JSON（截断 2000 字） |
| `cost_time` | 耗时（毫秒） |
| `oper_ip` | 客户端 IP |

后台「系统监控 → 操作日志」可查；小程序端暂未开放审计查询接口。

## 第二部分 开发规范

版本 V1.0 ｜ 2026-11-05 ｜ 适用于多人协作

> 目的：让每个人写的表、代码、接口、权限点在别人手里也能一眼看懂，减少合并冲突与联调返工。
> 原则：**沿用若依既有风格，物小助自有代码在此基础上统一命名**；若依原生 `sys_*` 表与后台代码不改造。

### 1. 目录与分层

```
ruoyi-system/src/main/java/com/ruoyi/business/
├── domain/        实体（对应 t_ 表）
├── mapper/        MyBatis 接口
└── service/       业务接口与 impl 子包
    └── task/      定时任务

ruoyi-admin/src/main/java/com/ruoyi/web/app/
├── controller/    小程序 JSON 接口
├── dto/           请求对象
└── config/        拦截器与调度注册

ruoyi-framework/src/main/java/com/ruoyi/framework/app/
                  令牌、上下文、权限、拦截器

ruoyi-common/src/main/java/com/ruoyi/common/
                  AppResult、@AppPermission 等公共件

ruoyi-system/src/main/resources/mapper/business/   Mapper XML
ruoyi-admin/src/main/resources/templates/business/ 打印模板
sql/                                               建表与初始化脚本
doc/                                               设计文档（全部 .md）
```

规则：**控制器只做协议适配与参数校验，业务规则放 Service，SQL 放 Mapper XML**。跨模块调用走 Service 接口，不直接注入别人的 Mapper。

### 2. 数据库命名

#### 2.1 表

| 规则 | 示例 |
| --- | --- |
| 业务表统一前缀 `t_`，名词用**单数** | `t_product`、`t_supplier`、`t_purchase_order` |
| 主表 + 明细表用主表名加后缀 | `t_purchase_order` / `t_purchase_order_item` |
| 中间表用两方名词 | `t_app_user_bind` |
| 全小写下划线，不用拼音缩写 | `t_replenish_suggestion`（不是 `t_bh_jy`） |
| 若依原生表保持 `sys_*` | `sys_user`、`sys_menu` |

#### 2.2 字段

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 普通字段 | 小写下划线 | `product_code`、`supplier_name` |
| 主键 | `{实体}_id` | `product_id`、`order_id`、`payable_id` |
| 外键 | 与被引用表主键同名 | `order_id`、`product_id` |
| 金额 | `decimal(18,2)`，后缀 `_amount` 或 `_price` | `total_amount`、`ref_price` |
| 数量 | `decimal(18,3)`，后缀 `_qty` | `qty`、`received_qty`、`in_transit_qty` |
| 状态 | `status char(1)` | `status` |
| 开关 | `{动作}_flag char(1)` | `enable_flag`、`del_flag` |
| 时间 | `datetime`，后缀 `_time` | `create_time`、`approve_time` |
| 日期 | `date`，后缀 `_date` | `due_date`、`calc_date` |
| 是否类 | 用 `char(1)` 不用 `boolean` | `'0'` 否 / `'1'` 是 |

#### 2.3 主键、索引、唯一键

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 主键 | `{实体}_id`，`bigint` 自增 | `PRIMARY KEY (order_id)` |
| 唯一键 | `uk_{表简称}_{字段缩写}` | `uk_product_code`、`uk_payable_order` |
| 普通索引 | `idx_{表简称}_{字段缩写}` | `idx_order_status`、`idx_stock_product` |
| 约束 | `ck_{表简称}_{含义}` | `ck_stock_qty` |

**多单位字段**：凡业务表必须含 `enterprise_id`，并把 `enterprise_id` 放进唯一键首位，例如 `uk_product_code (enterprise_id, product_code)`。

#### 2.4 通用字段

业务表统一包含（不需要就不加，但加了就按此命名）：

| 字段 | 含义 |
| --- | --- |
| `enterprise_id` | 单位ID，服务端注入 |
| `create_by` / `create_time` | 创建人 / 创建时间 |
| `update_by` / `update_time` | 更新人 / 更新时间 |
| `remark` | 备注 |
| `del_flag` | `'0'` 存在、`'2'` 删除（逻辑删除） |

#### 2.5 状态与枚举（已定，不得随意扩展）

| 字段 | 取值 |
| --- | --- |
| `t_purchase_order.status` | 0 草稿、1 待审批、2 已通过、3 已驳回、4 已完成、5 已取消 |
| `t_purchase_approval.result` | 1 通过、2 驳回 |
| `t_payable.status` | 0 未付款、1 部分付款、2 已结清 |
| `t_stock_record.record_type` | 1 入库、2 出库 |
| `t_replenish_suggestion.status` | 0 待处理、1 已建单、2 已忽略 |
| `t_ai_draft.status` | 0 待确认、1 已确认、2 已放弃、3 已过期 |
| `status`（人员/档案类） | 0 正常、1 停用 |
| `del_flag` | 0 存在、2 删除 |

新增状态值必须同时更新本表与 `接口说明.md`。

### 3. Java 命名

#### 3.1 包

```
com.ruoyi.business.<domain|mapper|service|service.impl|task>
com.ruoyi.web.app.<controller|dto|config>
com.ruoyi.framework.app
```

#### 3.2 类

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 实体 | 去掉 `t_`、驼峰单数 | `t_purchase_order` → `PurchaseOrder` |
| Mapper | 实体名 + `Mapper` | `PurchaseOrderMapper` |
| Service 接口 | `I` + 实体/聚合 + `Service` | `IPurchaseService` |
| Service 实现 | 同上去掉 I + `Impl` | `PurchaseServiceImpl` |
| 控制器 | `App` + 实体/模块 + `Controller` | `AppPurchaseController` |
| 请求对象 | 动作 + `Request` | `PaymentRequest`、`PurchaseActionRequest` |
| 统一响应 | `AppResult` | — |
| 定时任务 | 模块 + `Task` | `ReplenishTask` |
| 公共基类 | `AppBaseController`、`BizBase` | — |

#### 3.3 方法

| 动作 | 命名 |
| --- | --- |
| 查列表 | `selectXxxList` |
| 查单个 | `selectXxxById` |
| 新增 | `insertXxx` |
| 修改 | `updateXxx` |
| 逻辑删除 | `deleteXxxById` |
| 改状态 | `updateXxxStatus` |
| 计数 | `countByXxx` |
| 业务动作 | 动词原形：`submit`、`approve`、`reject`、`cancel`、`receive`、`calc`、`pay` |

控制器方法名与业务动作一致（`list`、`detail`、`add`、`edit`、`remove`），不要用 `doXxx`、`handleXxx`。

#### 3.4 变量、常量、注释

- 变量用驼峰，禁止 `a`、`tmp`、`list1`。
- 常量全大写下划线，定义在类顶部：`private static final int STAT_DAYS = 30;`
- 实体字段必须与表字段一一对应；仅用于展示/查询的字段在注释里注明“展示用/查询条件”。
- 类和方法写中文 Javadoc，说明**业务含义**而不是复述代码。
- 日志只记关键业务节点与异常：`log.info("补货计算完成，生成建议 {} 条", count)`，不打印手机号、口令、令牌。

### 4. 接口命名

#### 4.1 路径结构

```
/business/{模块}/{资源}[/{id}][/{动作}]
```

| 段 | 规则 | 示例 |
| --- | --- | --- |
| 模块 | 小写单数 | `product`、`purchase`、`payable`、`replenish` |
| 资源 | 小写单数，与模块同名时可省略 | `/business/product/list` |
| 动作 | 小写动词，子资源语义 | `/submit`、`/approve`、`/payment` |
| 分隔 | 一律用 `/`，不用驼峰、下划线 | `❌ /business/getProductList` |

#### 4.2 方法与语义

| 操作 | 方法 | 路径 |
| --- | --- | --- |
| 分页列表 | GET | `/business/product/list` |
| 详情 | GET | `/business/product/{id}` |
| 新增 | POST | `/business/product` |
| 全量修改 | PUT | `/business/product` 或 `/{id}` |
| 逻辑删除 | DELETE | `/business/product/{id}` |
| 状态变更 | PUT | `/business/product/{id}/status?status=0` |
| 业务动作 | POST | `/business/purchase/{id}/approve` |
| 文件下载 | GET | `/business/purchase/{id}/pdf` |

约定：**查询用 GET、变更用 POST/PUT/DELETE**；业务动作一律 POST，且路径以动词结尾。

#### 4.3 参数与响应

| 项 | 约定 |
| --- | --- |
| 分页参数 | `pageNum`（默认 1）、`pageSize`（默认 10，约定不超过 100） |
| 列表响应 | `{ code, msg, rows, total }` |
| 单对象响应 | `{ code, msg, data }` |
| 动作响应 | `{ code, msg }`，需要返回主键时加 `orderId` 等字段 |
| 字段风格 | 驼峰，与实体一致；下划线只在数据库出现 |
| 时间格式 | `yyyy-MM-dd HH:mm:ss` |
| 金额 | `decimal(18,2)`，JSON 中为数值（如 `1000.00`） |
| 幂等 | 写接口必须带 `X-Request-Id`（UUID），重复返回 409；审计自动落 `sys_oper_log` |
| 单位标识 | 不接受前端传 `enterpriseId`，一律取令牌 |

#### 4.4 错误码

| 码 | 含义 |
| --- | --- |
| 200 | 成功 |
| 401 | 未登录或令牌失效 |
| 403 | 无权限 |
| 500 | 业务校验失败或服务异常 |

HTTP 状态统一 200，业务码放在 `code` 里（前端按 `code` 判断）。

#### 4.5 权限点

格式：`business:{模块}:{动作}`

| 权限点 | 用途 |
| --- | --- |
| `business:product:edit` | 商品增改删 |
| `business:supplier:edit` | 供应商增改删 |
| `business:category:edit` | 分类维护 |
| `business:stock:edit` | 出入库、收货 |
| `business:purchase:edit` | 建单、编辑、提交、取消 |
| `business:purchase:approve` | 审批通过/驳回 |
| `business:payable:edit` | 付款登记 |
| `business:replenish:edit` | 补货参数与计算 |
| `business:enterprise:edit` | 单位信息 |
| `business:export` | 数据导出 |

规则：**一个权限点只对应一类操作**；新增权限点必须同时写入 `sql/cangxiaozhu_menu.sql` 与 `接口说明.md`。查询类接口默认登录即可访问，不加权限点。

### 5. 小程序端约定

前端由前端同学维护，命名保持与后端对齐：

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 页面目录 | `pages/{模块}/` | `pages/purchase/` |

### 6. 配置与缓存

| 对象 | 规则 | 现有示例 |
| --- | --- | --- |

- 类名：`{模块}Task`，方法名 `run`；
- cron 走配置：`cangxiaozhu.task.{模块}-cron`；

- 新增任务写进 `部署运行说明.md` 的任务表。

### 9. 新增业务模块检查清单

1. 设计表：`t_{模块}` + 明细表，含 `enterprise_id` 与通用字段；
2. 写进 `sql/cangxiaozhu_schema.sql`（可重复执行），本地重建验证；
3. `domain` 实体继承 `BizBase`（需要通用字段时）；
4. `mapper` 接口 + `mapper/business/XxxMapper.xml`，字段全部 `as` 成驼峰；
5. `service` 接口与实现，事务加在写方法上；
6. `AppXxxController` 继承 `AppBaseController`，写接口加 `@AppPermission`；
7. 权限点写入 `sql/cangxiaozhu_menu.sql` 并挂到对应角色；
8. 更新 `doc/接口说明.md`（路径、参数、响应、错误）；
9. 更新 `readme.md` 进度；
10. `mvn -B -DskipTests clean package` + 接口冒烟（登录 → 列表 → 新增 → 校验 → 异常分支）。
