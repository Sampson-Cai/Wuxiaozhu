# 接口说明（基础功能）

> 基址示例：`http://127.0.0.1:18080`
> 命名与协作约定见 [开发规范](开发规范.md)。
> 已实现：认证、单位信息、商品分类、商品、供应商、库存出入库、采购单与单级审批、收货入库（自动生成应付）、
> 应付账款与付款、补货参数与计算、首页预警与趋势、Excel 导出、采购单 PDF。
> AI 助手需接入真实模型服务（readme 问题 005），尚未实现。

## 1. 通用约定

| 项 | 约定 |
| --- | --- |
| 鉴权头 | `Authorization: Bearer <token>`；文件下载可用 `?token=` |
| 内容类型 | `application/json; charset=utf-8`（写接口） |
| 成功响应 | `{ "code": 200, "msg": "操作成功", ... }` |
| 分页响应 | `{ "code": 200, "rows": [...], "total": 12 }` |
| 分页参数 | `pageNum`（默认 1）、`pageSize`（默认 10，最大 100） |
| 未登录 | `{ "code": 401, "msg": "登录状态已过期，请重新登录" }` |
| 无权限 | `{ "code": 403, "msg": "没有操作权限：xxx" }` |
| 业务失败 | `{ "code": 500, "msg": "具体原因" }` |
| 单位隔离 | 单位 ID 只取自令牌，请求体中出现的 enterpriseId 一律忽略 |

## 2. 认证

### 2.1 图形验证码

```
GET /captchaImage?type=math
```

`type`：`math`（默认，算术）/ `char`（字符）。

```json
{ "code": 200, "uuid": "1f3c...", "img": "/9j/4AAQSkZJRg..." }
```

`img` 为 Base64 JPEG，前端拼 `data:image/jpeg;base64,` 后展示；`uuid` 2 分钟内有效，校验后即失效。

### 2.2 登录

```
POST /login
Content-Type: application/x-www-form-urlencoded

username=admin&password=admin123&code=12&uuid=1f3c...
```

验证码关闭时可省略 `code`、`uuid`。

```json
{ "code": 200, "msg": "登录成功", "token": "OaSJuyvRyMVG421QWkHutwNdy23YsjtibYs5hDXFSYU" }
```

失败：`{"code":500,"msg":"验证码错误"}` / `{"code":500,"msg":"用户或密码错误"}`。

### 2.3 当前用户

```
GET /getInfo
Authorization: Bearer <token>
```

```json
{
  "code": 200,
  "user": { "userId": 1, "userName": "admin", "nickName": "若依", "deptId": 103, "avatar": "", "email": "ry@163.com", "phonenumber": "15888888888", "loginDate": "2026-11-05 10:57:15" },
  "roles": ["admin"],
  "permissions": ["*:*:*"]
}
```

### 2.4 退出

```
POST /logout
Authorization: Bearer <token>
```

```json
{ "code": 200, "msg": "退出成功" }
```

令牌立即失效。后台 Web 仍可用 `GET /logout` 清会话后跳转登录页。

## 7. 库存

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/business/stock/list` | 登录 | 分页；`keyword` 匹配名称/编码，`categoryId` 按分类，`lowStockOnly=true` 只看预警 |
| GET | `/business/stock/{productId}` | 登录 | 单品库存 |
| GET | `/business/stock/records` | 登录 | 流水分页；`productId`、`recordType`（1 入库 / 2 出库）、`beginTime`、`endTime` |
| POST | `/business/stock/inbound` | `business:stock:edit` | 入库 |
| POST | `/business/stock/outbound` | `business:stock:edit` | 出库（可用量不足拒绝） |
| POST | `/business/stock/records/{recordId}/reverse` | `business:stock:edit` | 冲销手工流水，body 可带 `remark` |

库存字段补充：`qty` 现存、`lockedQty` 锁定、`inTransitQty` 在途、`availableQty` 可用（服务端计算）、`safetyStock` 安全库存（取自补货参数）、`stockStatus`（0 正常 / 1 低于安全库存 / 2 缺货）。

入库请求：

```json
{ "productId": 1, "qty": 100, "bizType": "其他入库", "batchNo": "B20261105", "remark": "首次入库" }
```

出库请求：

```json
{ "productId": 1, "qty": 30, "bizType": "领用出库", "remark": "部门领用" }
```

返回：`{"code":200,"msg":"入库成功"}`；数量 ≤ 0 或超量出库返回 500 与具体原因。

流水记录包含 `beforeQty`、`afterQty`、`operatorName`、`bizType`、`sourceNo`、`batchNo`、`reverseFlag`、`reverseRecordId`，可用于对账。

冲销规则：

- 仅允许冲销 `sourceNo` 为空的手工出入库流水；采购入库等单据来源流水必须走原单据流程；
- 原入库冲销生成一笔出库，原出库冲销生成一笔入库，数量相同，`bizType = 冲销`；
- 原入库冲销要求当前库存足够，否则返回「当前库存不足以冲销该入库流水」；
- 原流水 `reverseFlag` 置为 `1`，重复冲销返回「该流水已冲销，不能重复冲销」；
- 补货计算只统计未冲销的出库流水。

## 8. 采购单与审批

状态：`0 草稿 / 1 待审批 / 2 已通过 / 3 已驳回 / 4 已完成 / 5 已取消`

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/business/purchase/list` | 登录 | 分页；`status`、`keyword`（单号/供应商）、`beginTime`、`endTime`（创建日期） |
| GET | `/business/purchase/todo` | 登录 | 待审批列表（status=1） |
| GET | `/business/purchase/{orderId}` | 登录 | 详情：单据 + 明细 + 审批记录 |
| POST | `/business/purchase` | `business:purchase:edit` | 新建草稿 |
| PUT | `/business/purchase/{orderId}` | `business:purchase:edit` | 编辑（仅草稿/已驳回） |
| DELETE | `/business/purchase/{orderId}` | `business:purchase:edit` | 删除草稿（逻辑删除，仅 status=0） |
| POST | `/business/purchase/{orderId}/submit` | `business:purchase:edit` | 提交审批 |
| POST | `/business/purchase/{orderId}/approve` | `business:purchase:approve` | 通过，body 可带 `opinion` |
| POST | `/business/purchase/{orderId}/reject` | `business:purchase:approve` | 驳回，`opinion` 必填 |
| POST | `/business/purchase/{orderId}/cancel` | `business:purchase:edit` | 取消，`reason` 必填 |
| POST | `/business/purchase/{orderId}/receive` | `business:stock:edit` | 收货入库，body 可带 `remark`；分批收货传 `items` |

创建请求：

```json
{
  "supplierId": 1,
  "remark": "十月办公用品采购",
  "items": [
    { "productId": 1, "qty": 50, "price": 20 },
    { "productId": 2, "qty": 10, "price": 35.5 }
  ]
}
```

服务端按商品档案补全名称、规格、单位，金额 = 数量 × 单价，总额自动汇总；`supplierId` 必须为启用供应商。

业务联动：

- 提交：状态 0/3 → 1，版本号 +1；
- 通过：状态 1 → 2，写审批记录，按明细累加库存**在途量**；
- 驳回：状态 1 → 3，审批意见必填，可编辑后重新提交（版本继续递增）；
- 取消：状态 1/2 → 5，已通过的单据取消时冲减在途量；已部分收货的单据不允许取消；
- 删除：仅状态 0（草稿）可删，逻辑删除 `del_flag='2'`，明细不物理删除；重复删除返回“采购单不存在”；
- 收货：生成收货单与入库流水（`sourceNo` = 采购单号），冲减在途、增加库存；全部明细收完后状态 2 → 4，并按订单金额与供应商账期生成应付账款；
- 分批收货：body 传 `items` 只收指定明细，未传则按待收数量全部收货；部分收货后单据保持「已通过」，可继续收货，应付只在收完时生成一笔；

```json
{ "remark": "首批到货", "items": [ { "itemId": 11, "qty": 20 }, { "itemId": 12, "qty": 5 } ] }
```

- 管理员（userId=1）可代审并留痕，其他审批人不得审批自己创建的单据。

## 10. 补货

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/business/replenish/param/{productId}` | 登录 | 读取参数，无记录时返回默认值（周期 7 天、交期 3 天、系数 1.00） |
| PUT | `/business/replenish/param/{productId}` | `business:replenish:edit` | 保存参数（季节系数 0.80–1.50） |
| GET | `/business/replenish/suggestions` | 登录 | 分页；`status`、`keyword` |
| POST | `/business/replenish/calc` | `business:replenish:edit` | 手动触发计算，返回生成条数 |
| POST | `/business/replenish/suggestion/{id}/to-purchase` | `business:purchase:edit` | 建议转采购草稿，返回 `orderId`；商品需有默认供应商 |
| PUT | `/business/replenish/suggestion/{id}/status?status=2` | `business:replenish:edit` | 忽略建议（仅支持 2） |

参数请求：

```json
{ "safetyStock": 20, "maxStock": 200, "cycleDays": 7, "leadDays": 3, "seasonCoef": 1.2, "enableFlag": "1" }
```

计算口径：

```
d = 近 30 天出库量 / 30
G = max(安全库存, d × (周期 + 交期) × 季节系数)
Q = ceil(G − 可用库存 − 在途采购量)
Q = min(Q, 最大库存 − 可用库存 − 在途采购量)
Q ≤ 0 时不生成建议
```

定时任务每天 02:00 遍历启用单位执行（`cangxiaozhu.task.replenish-cron` 可改）。

## 14. 联调示例

```bash
# 登录
TOKEN=$(curl -s -X POST http://127.0.0.1:18080/login \
  -d "username=admin&password=admin123" | sed 's/.*"token":"\([^"]*\)".*/\1/')

# 新增分类
curl -X POST http://127.0.0.1:18080/business/category \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"办公用品","sort":1}'

# 入库
curl -X POST http://127.0.0.1:18080/business/stock/inbound \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"productId":1,"qty":100,"bizType":"其他入库"}'
```

> Windows 命令行直接拼中文 JSON 容易因 GBK 编码被服务端拒绝（`JSON parse error: Invalid UTF-8`），建议把请求体写入 UTF-8 文件后用 `--data-binary @file` 发送。

新增请求：

```json
{ "loginName": "zhangsan", "userName": "张三", "password": "123456",
  "phonenumber": "13800000000", "email": "zs@example.com", "roleIds": [101] }
```

规则：

- 登录账号 2–20 位、单位内唯一；初始密码不少于 6 位；
- 单位标识、盐值、口令密文、创建人由服务端注入，前端传了也会被覆盖；
- 口令加密与后台一致（`md5(loginName + password + salt)`），否则新账号无法登录；
- 不能修改/停用/重置超级管理员（userId=1），本人除外。

### 16.2 角色

## 17. 智能检索

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/business/search/product?q=找到一台电脑的配套螺丝&limit=10` | 登录 | 自然语言/关键词检索商品，按相关度排序 |

返回：

```json
{
  "code": 200,
  "total": 1,
  "query": "找到一台电脑的配套螺丝",
  "rows": [
    { "productId": 3, "productCode": "P003", "productName": "笔记本专用螺丝 M2×5",
      "spec": "M2×5 不锈钢", "unit": "包", "stockQty": 0, "score": 1.0,
      "matchedTerms": ["笔记本", "螺丝"] }
  ]
}
```

匹配规则：

1. 先去掉"的、一台、帮我、配套"等口语词；
2. 把问题拆成概念，每个概念带近义词（电脑→计算机/笔记本/PC/台式机，螺丝→螺钉/螺栓/紧固件）；
3. 商品命中任一近义词即算命中该概念，名称权重 3、规格/编码 2、分类/备注 1；
4. `score = 命中权重 / (概念数 × 3)`，`matchedTerms` 给出命中的词，方便前端解释"为什么是这条"。

能力边界：这是**词法 + 同义词**匹配，可解释、无外部依赖，但无法理解"配套/兼容/可替代"这类语义关系。
真正的语义检索需要 Embedding 模型与向量库，接入方式见 `企划书` 第 6.7 节；届时本接口改为
"先向量召回、再走同一套打分兜底"，前端无需改动。


## 18. 幂等与审计

### 18.1 幂等

- 所有写接口（POST/PUT/DELETE）必须带 `X-Request-Id`（建议 UUID）；
- 服务端以 `(enterprise_id, request_id)` 唯一键占位：首次执行、重复拦截；
- 缺失幂等键返回 500，重复提交返回 409；
- 上次执行失败时，允许用同一 `requestId` 重试（记录状态会回到处理中）；
- 记录保留 7 天，每天 03:30 清理，`cangxiaozhu.task.idem-clean-cron` 可调；
- `cangxiaozhu.idempotent.enabled=false` 可临时关闭，不建议用于生产。

### 18.2 审计

`/business/**` 下所有非查询请求自动写入若依 `sys_oper_log`：

| 字段 | 内容 |
| --- | --- |
| `oper_name` | 当前登录账号 |
| `title` / `oper_url` | 请求路径 |
| `request_method` | POST / PUT / DELETE |
| `operator_type` | 2（移动端） |
| `status` | 0 成功 / 1 失败（按业务 code 判定） |
| `error_msg` | 失败原因 |
| `json_result` | 响应 JSON（截断 2000 字） |
| `cost_time` | 耗时（毫秒） |
| `oper_ip` | 客户端 IP |

后台「系统监控 → 操作日志」可查；小程序端接口见第 19 节。

## 20. AI 助手与知识库（RAG）

模型：

| 能力 | 供应商 | 模型 | 接口 |
| --- | --- | --- | --- |
| 对话 | DeepSeek | DeepSeek-V4.1-Flash（API id `deepseek-flash`） | `POST https://api.deepseek.com/chat/completions` |
| 向量 | 硅基流动 | `Qwen/Qwen3-Embedding-8B`（4096 维） | `POST https://api.siliconflow.cn/v1/embeddings` |

配置在 `application.yml` 的 `ai` 段，密钥支持 `AI_CHAT_KEY` / `AI_EMBEDDING_KEY` 环境变量覆盖。

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/business/ai/status` | 登录 | 是否启用、模型名、文档数、片段数 |
| POST | `/business/ai/chat` | 登录 | body `{sessionId, question}`，返回 `{sessionId, answer, sources, model, tokens, costMs}` |
| POST | `/business/ai/chat/stream` | 登录 | 同上，SSE 流式返回：`meta` → `delta`(多次) → `done`；出错为 `error` |
| GET | `/business/ai/sessions` | 登录 | 我的会话，按更新时间倒序 |
| GET | `/business/ai/sessions/{sessionId}/messages` | 登录 | 会话消息 |
| GET | `/business/ai/kb/documents` | 登录 | 知识库文档与切片状态 |
| POST | `/business/ai/kb/import` | `business:kb:edit` | body `{path, docType}`，导入服务器本地 `.md/.txt/.csv`，自动切片并向量化 |
| POST | `/business/ai/kb/{documentId}/reindex` | `business:kb:edit` | 重新向量化 |
| DELETE | `/business/ai/kb/{documentId}` | `business:kb:edit` | 删除文档与片段 |

流式接口（`/chat/stream`）事件格式：

```
event: meta
data: {"sessionId":20,"sources":[{"documentId":1,"title":"仓库物品数据","score":0.628}]}

event: delta
data: {"text":"结论"}

event: done
data: {"tokens":1234,"costMs":4321,"length":210}
```

- 首帧 `meta` 在检索完成后立即下发（约 0.5~1s），前端可先渲染来源；
- `delta` 为增量文本，逐段追加即可；
- nginx 对该路径单独关闭了 `proxy_buffering` 与 `gzip`，否则会被攒成整包；
- 小程序端需 `wx.request({ enableChunked: true })` + `onChunkReceived`，`uni.request` 部分版本会丢掉该参数。

回答流程：

1. 问题向量化 → 与 `t_kb_chunk` 全量向量算余弦，取 `top-k`（默认 5）且分数 ≥ `min-score`（默认 0.32）；
2. 从命中片段里识别物料编码（如 `NUT-HX-004`），回查 `t_product` / `t_stock`，把**实时单价与现存**补进提示词，避免模型引用过期数字；
3. 拼装系统提示词：角色规则 + 实时业务快照（预警数、待审批、应付、低库存明细）+ 相关商品实时数据 + 知识库片段；
4. 调对话模型，落 `t_ai_chat_session` / `t_ai_chat_message`，`sources` 按文档去重后返回。

切片规则（`MarkdownChunker`）：按 `#` 标题分段，单段超过 700 字再按行切块，相邻块重叠 120 字；表格被切断时后续块重复表头，保证每块可独立阅读。

向量存储：`t_kb_chunk.embedding` 存 float32 小端 + Base64（4096 维约 22KB），检索时解码后内存计算；单单位索引缓存 5 分钟，导入/删除即失效。片段上万时再换专用向量库。

降级：`ai.enabled=false` 或模型调用失败时，小程序自动回落到本地「数据问答」（`utils/assistant.js`，只查业务接口，不编造）。
