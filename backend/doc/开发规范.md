# 物小助开发规范

版本 V1.0 ｜ 2026-11-05 ｜ 适用于多人协作

> 目的：让每个人写的表、代码、接口、权限点在别人手里也能一眼看懂，减少合并冲突与联调返工。
> 原则：**沿用若依既有风格，物小助自有代码在此基础上统一命名**；若依原生 `sys_*` 表与后台代码不改造。

## 1. 目录与分层

```
ruoyi-system/src/main/java/com/ruoyi/business/
├── domain/        实体（对应 t_ 表）
├── mapper/        MyBatis 接口
└── service/       业务接口与 impl 子包
    └── task/      定时任务

ruoyi-admin/src/main/java/com/ruoyi/web/app/
├── controller/    小程序 JSON 接口
├── dto/           请求对象
└── config/        拦截器与调度注册

ruoyi-framework/src/main/java/com/ruoyi/framework/app/
                  令牌、上下文、权限、拦截器

ruoyi-common/src/main/java/com/ruoyi/common/
                  AppResult、@AppPermission 等公共件

ruoyi-system/src/main/resources/mapper/business/   Mapper XML
ruoyi-admin/src/main/resources/templates/business/ 打印模板
sql/                                               建表与初始化脚本
doc/                                               设计文档（全部 .md）
```

规则：**控制器只做协议适配与参数校验，业务规则放 Service，SQL 放 Mapper XML**。跨模块调用走 Service 接口，不直接注入别人的 Mapper。

分层例外（2026-11-05 新增）：**档案类单表删除的引用校验允许写在控制器**，沿用 `AppCategoryController.remove` 的既有写法
（`countXxxByYyy` 计数后直接返回提示语），不再为其单独建 Service；涉及多表状态流转或删除后影响其他单据的，仍在 Service
（如 `PurchaseServiceImpl.delete`）。同一 `com.ruoyi.business` 包内注入其他模块的 Mapper 不算跨模块，`business` 与
`system`/`web` 之间才走 Service 接口。

## 2. 数据库命名

### 2.1 表

| 规则 | 示例 |
| --- | --- |
| 业务表统一前缀 `t_`，名词用**单数** | `t_product`、`t_supplier`、`t_purchase_order` |
| 主表 + 明细表用主表名加后缀 | `t_purchase_order` / `t_purchase_order_item` |
| 中间表用两方名词 | `t_app_user_bind` |
| 全小写下划线，不用拼音缩写 | `t_replenish_suggestion`（不是 `t_bh_jy`） |
| 若依原生表保持 `sys_*` | `sys_user`、`sys_menu` |

### 2.2 字段

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 普通字段 | 小写下划线 | `product_code`、`supplier_name` |
| 主键 | `{实体}_id` | `product_id`、`order_id`、`payable_id` |
| 外键 | 与被引用表主键同名 | `order_id`、`product_id` |
| 金额 | `decimal(18,2)`，后缀 `_amount` 或 `_price` | `total_amount`、`ref_price` |
| 数量 | `decimal(18,3)`，后缀 `_qty` | `qty`、`received_qty`、`in_transit_qty` |
| 状态 | `status char(1)` | `status` |
| 开关 | `{动作}_flag char(1)` | `enable_flag`、`del_flag` |
| 时间 | `datetime`，后缀 `_time` | `create_time`、`approve_time` |
| 日期 | `date`，后缀 `_date` | `due_date`、`calc_date` |
| 是否类 | 用 `char(1)` 不用 `boolean` | `'0'` 否 / `'1'` 是 |

### 2.3 主键、索引、唯一键

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 主键 | `{实体}_id`，`bigint` 自增 | `PRIMARY KEY (order_id)` |
| 唯一键 | `uk_{表简称}_{字段缩写}` | `uk_product_code`、`uk_payable_order` |
| 普通索引 | `idx_{表简称}_{字段缩写}` | `idx_order_status`、`idx_stock_product` |
| 约束 | `ck_{表简称}_{含义}` | `ck_stock_qty` |

**多单位字段**：凡业务表必须含 `enterprise_id`，并把 `enterprise_id` 放进唯一键首位，例如 `uk_product_code (enterprise_id, product_code)`。

### 2.4 通用字段

业务表统一包含（不需要就不加，但加了就按此命名）：

| 字段 | 含义 |
| --- | --- |
| `enterprise_id` | 单位ID，服务端注入 |
| `create_by` / `create_time` | 创建人 / 创建时间 |
| `update_by` / `update_time` | 更新人 / 更新时间 |
| `remark` | 备注 |
| `del_flag` | `'0'` 存在、`'2'` 删除（逻辑删除） |

### 2.5 状态与枚举（已定，不得随意扩展）

| 字段 | 取值 |
| --- | --- |
| `t_purchase_order.status` | 0 草稿、1 待审批、2 已通过、3 已驳回、4 已完成、5 已取消 |
| `t_purchase_approval.result` | 1 通过、2 驳回 |
| `t_payable.status` | 0 未付款、1 部分付款、2 已结清 |
| `t_stock_record.record_type` | 1 入库、2 出库 |
| `t_stock_record.reverse_flag` | 0 未冲销、1 已冲销 |
| `t_replenish_suggestion.status` | 0 待处理、1 已建单、2 已忽略 |
| `t_ai_draft.status` | 0 待确认、1 已确认、2 已放弃、3 已过期 |
| `status`（人员/档案类） | 0 正常、1 停用 |
| `del_flag` | 0 存在、2 删除 |

新增状态值必须同时更新本表与 `接口说明.md`。

## 3. Java 命名

### 3.1 包

```
com.ruoyi.business.<domain|mapper|service|service.impl|task>
com.ruoyi.web.app.<controller|dto|config>
com.ruoyi.framework.app
```

### 3.2 类

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 实体 | 去掉 `t_`、驼峰单数 | `t_purchase_order` → `PurchaseOrder` |
| Mapper | 实体名 + `Mapper` | `PurchaseOrderMapper` |
| Service 接口 | `I` + 实体/聚合 + `Service` | `IPurchaseService` |
| Service 实现 | 同上去掉 I + `Impl` | `PurchaseServiceImpl` |
| 控制器 | `App` + 实体/模块 + `Controller` | `AppPurchaseController` |
| 请求对象 | 动作 + `Request` | `PaymentRequest`、`PurchaseActionRequest` |
| 统一响应 | `AppResult` | — |
| 定时任务 | 模块 + `Task` | `ReplenishTask` |
| 公共基类 | `AppBaseController`、`BizBase` | — |

### 3.3 方法

| 动作 | 命名 |
| --- | --- |
| 查列表 | `selectXxxList` |
| 查单个 | `selectXxxById` |
| 新增 | `insertXxx` |
| 修改 | `updateXxx` |
| 逻辑删除 | `deleteXxxById` |
| 改状态 | `updateXxxStatus` |
| 计数 | `countByXxx` |
| 业务动作 | 动词原形：`submit`、`approve`、`reject`、`cancel`、`receive`、`calc`、`pay` |

控制器方法名与业务动作一致（`list`、`detail`、`add`、`edit`、`remove`），不要用 `doXxx`、`handleXxx`。

计数与删除命名细化（2026-11-05 新增）：

| 动作 | 命名 |
| --- | --- |
| 计数（唯一性校验） | `countByXxx`，按待校验字段命名：`countByCode` |
| 计数（引用关系校验） | `count{被引用记录}By{主体}`：`countPurchaseItemsByProduct`、`countOrdersBySupplier`、`countUnpaidPayablesBySupplier`、`countProductsBySupplier` |
| 逻辑删除 | 一律 `deleteXxxById`；交接单原文的 `deleteOrder` 已按此规则改为 `deleteOrderById` |
| 业务动作（删除） | Service 方法用 `delete`，控制器方法用 `remove`，与 `submit`、`cancel` 等并列用动词原形 |

引用计数规则：SQL 条件必须排除已逻辑删除的记录（`del_flag = '0'`）；无 `del_flag` 的表（如 `t_payable`）按状态判定
（`status != '2'`）。新增同类校验照此命名，不再写 `countPurchaseItems`、`countOrders` 这类看不出主体的名字。

### 3.4 变量、常量、注释

- 变量用驼峰，禁止 `a`、`tmp`、`list1`。
- 常量全大写下划线，定义在类顶部：`private static final int STAT_DAYS = 30;`
- 实体字段必须与表字段一一对应；仅用于展示/查询的字段在注释里注明“展示用/查询条件”。
- 类和方法写中文 Javadoc，说明**业务含义**而不是复述代码。
- 日志只记关键业务节点与异常：`log.info("补货计算完成，生成建议 {} 条", count)`，不打印手机号、口令、令牌。

## 4. 接口命名

### 4.1 路径结构

```
/business/{模块}/{资源}[/{id}][/{动作}]
```

| 段 | 规则 | 示例 |
| --- | --- | --- |
| 模块 | 小写单数 | `product`、`purchase`、`payable`、`replenish` |
| 资源 | 小写单数，与模块同名时可省略 | `/business/product/list` |
| 动作 | 小写动词，子资源语义 | `/submit`、`/approve`、`/payment` |
| 分隔 | 一律用 `/`，不用驼峰、下划线 | `❌ /business/getProductList` |

### 4.2 方法与语义

| 操作 | 方法 | 路径 |
| --- | --- | --- |
| 分页列表 | GET | `/business/product/list` |
| 详情 | GET | `/business/product/{id}` |
| 新增 | POST | `/business/product` |
| 全量修改 | PUT | `/business/product` 或 `/{id}` |
| 逻辑删除 | DELETE | `/business/product/{id}` |
| 状态变更 | PUT | `/business/product/{id}/status?status=0` |
| 业务动作 | POST | `/business/purchase/{id}/approve` |
| 文件下载 | GET | `/business/purchase/{id}/pdf` |

约定：**查询用 GET、变更用 POST/PUT/DELETE**；业务动作一律 POST，且路径以动词结尾。

删除接口语义（2026-11-05 新增）：`DELETE /business/{模块}/{id}` 只做逻辑删除，且**必须先过引用校验**；
不允许出现“无校验的裸删除”。没有删除接口的实体一律用状态位表达终止（采购单用取消、库存流水与付款记录不可删、
补货参数用 `enableFlag` 停用、账号用停用）。

### 4.3 参数与响应

| 项 | 约定 |
| --- | --- |
| 分页参数 | `pageNum`（默认 1）、`pageSize`（默认 10，约定不超过 100） |
| 列表响应 | `{ code, msg, rows, total }` |
| 单对象响应 | `{ code, msg, data }` |
| 动作响应 | `{ code, msg }`，需要返回主键时加 `orderId` 等字段 |
| 字段风格 | 驼峰，与实体一致；下划线只在数据库出现 |
| 时间格式 | `yyyy-MM-dd HH:mm:ss` |
| 金额 | `decimal(18,2)`，JSON 中为数值（如 `1000.00`） |
| 幂等 | 写接口必须带 `X-Request-Id`（UUID），重复返回 409；审计自动落 `sys_oper_log` |
| 单位标识 | 不接受前端传 `enterpriseId`，一律取令牌 |
| 删除被拒提示语 | 统一「该{对象}已被{引用方}{动作}，建议改为停用」/「该{对象}仍有{数据}，请先{处理}或改为停用」，必须指向对应停用接口，不返回裸异常 |

### 4.4 错误码

| 码 | 含义 |
| --- | --- |
| 200 | 成功 |
| 401 | 未登录或令牌失效 |
| 403 | 无权限 |
| 500 | 业务校验失败或服务异常 |

HTTP 状态统一 200，业务码放在 `code` 里（前端按 `code` 判断）。

### 4.5 权限点

格式：`business:{模块}:{动作}`

| 权限点 | 用途 |
| --- | --- |
| `business:product:edit` | 商品增改删 |
| `business:supplier:edit` | 供应商增改删 |
| `business:category:edit` | 分类维护 |
| `business:stock:edit` | 出入库、收货 |
| `business:purchase:edit` | 建单、编辑、提交、取消 |
| `business:purchase:approve` | 审批通过/驳回 |
| `business:payable:edit` | 付款登记 |
| `business:replenish:edit` | 补货参数与计算 |
| `business:enterprise:edit` | 单位信息 |
| `business:export` | 数据导出 |

规则：**一个权限点只对应一类操作**；新增权限点必须同时写入 `sql/cangxiaozhu_menu.sql` 与 `接口说明.md`。查询类接口默认登录即可访问，不加权限点。

## 5. 小程序端约定

前端由前端同学维护，命名保持与后端对齐：

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 页面目录 | `pages/{模块}/` | `pages/purchase/` |

| 组件 | kebab-case，带业务前缀 | `approval-timeline`、`draft-card` |
| 请求方法 | 按接口语义封装：`getXxxList`、`submitXxx` | `submitPurchase` |
| 状态常量 | 与后端码值一致，集中在一个 constants 文件 | `PURCHASE_STATUS` |

页面与接口的对应关系写进 `doc/接口说明.md` 的模块小节，避免两端各说各话。

## 6. 配置与缓存

| 对象 | 规则 | 现有示例 |
| --- | --- | --- |
| 业务配置 | `cangxiaozhu.{域}.{项}`，kebab-case | `cangxiaozhu.pdf.font-path`、`cangxiaozhu.task.replenish-cron` |

## 7. 定时任务

- 类名：`{模块}Task`，方法名 `run`；
- cron 走配置：`cangxiaozhu.task.{模块}-cron`；
- 任务必须可重入、失败不影响其他单位（遍历单位时逐个 try/catch）；
- 新增任务写进 `部署运行说明.md` 的任务表。

## 9. 新增业务模块检查清单

1. 设计表：`t_{模块}` + 明细表，含 `enterprise_id` 与通用字段；
2. 写进 `sql/cangxiaozhu_schema.sql`（可重复执行），本地重建验证；
3. `domain` 实体继承 `BizBase`（需要通用字段时）；
4. `mapper` 接口 + `mapper/business/XxxMapper.xml`，字段全部 `as` 成驼峰；
5. `service` 接口与实现，事务加在写方法上；
6. `AppXxxController` 继承 `AppBaseController`，写接口加 `@AppPermission`；
7. 权限点写入 `sql/cangxiaozhu_menu.sql` 并挂到对应角色；
8. 更新 `doc/接口说明.md`（路径、参数、响应、错误）；
9. 更新 `readme.md` 进度；
10. `mvn -B -DskipTests clean package` + 接口冒烟（登录 → 列表 → 新增 → 校验 → 异常分支）。

## 9. AI 与知识库

| 约定 | 说明 |
| --- | --- |
| 模型配置 | 一律放 `application.yml` 的 `ai` 段，密钥用 `${ENV:默认值}`，禁止硬编码在 Java 里 |
| 提示词 | 系统提示词由 `AiChatServiceImpl.systemPrompt` 统一拼装，顺序固定：角色规则 → 实时快照 → 相关商品实时数据 → 知识库片段 |
| 事实来源 | 只允许来自「知识库片段」「实时业务快照」「相关商品实时数据」；三者都没有时明确回答「系统里查不到」，不得编造 |
| 引用 | 每个事实句末标注（来源：文档标题），前端 `sources` 按文档去重 |
| 切片 | 走 `MarkdownChunker`，按标题分段 + 定长切块 + 表格表头复用；不要按固定字数硬切正文 |
| 向量 | 存 `t_kb_chunk.embedding`（float32 Base64）+ `dim` + `embedding_model`；换模型必须 `reindex` 并同步 `ai.embedding.dim` |
| 会话 | 一问一答都落 `t_ai_chat_session` / `t_ai_chat_message`，`sources` 存 JSON；不删除历史，只按会话查询 |
| 降级 | 模型不可用时接口抛 `ServiceException`，前端回落到本地数据问答；不得返回模拟回答 |
| 权限 | 对话仅需登录；知识库增删改走 `business:kb:edit` |

## 10. 小程序 UI 规范

设计依据：`ui-ux-pro-max`（GitHub: nextlevelbuilder/ui-ux-pro-max-skill，已装到 `~/.workbuddy-ai/skills/ui-ux-pro-max`）+ Apple HIG。核心是「按压不改变布局、内容不被固定栏遮挡、点击目标够大」。

### 10.1 按压态

| 规则 | 做法 | 禁止 |
| --- | --- | --- |
| 必须有反馈 | 列表用 `ios-cell-hover`（底色）、按钮用 `ios-btn-hover`（透明度）、文字/图标用 `tap-hover`（透明度 0.55） | 可点击但无任何视觉变化 |
| 不改布局 | 只改 `background-color` / `opacity`；`transform: scale` 必须配 `transition: 0.12s` | 改 `padding`、`margin`、`height`、`border-width`，会让周围内容跳动 |
| 反馈时延 | 按下即变色，松手恢复；不做 200ms 以上延迟动画 | 点击后无响应或延迟变色 |
| 形状一致 | 按压底色必须与元素形状一致：宫格/卡片用专属 hover 类，带同样的 `border-radius`，四周内缩 6rpx | 复用列表行的 `ios-cell-hover`，方角铺满整格，看起来像错位的半透明块 |

### 10.2 点击目标

| 元素 | 最小尺寸 | 说明 |
| --- | --- | --- |
| 列表行 `ios-cell` | 96rpx（48pt） | 全局已设 `min-height` |
| 主按钮 `ios-btn` | 96rpx | 底部操作栏按钮 |
| 图标按钮（新增/发送） | 72~80rpx | 小于 88rpx 时靠四周留白补足 |
| 筛选 chip | 68rpx | 横向较宽，纵向不低于 68rpx |
| 纯文字按钮 | 上下 `padding` ≥ 14rpx | 否则点不中 |

### 10.3 固定元素与安全区

- 底部固定栏必须 `padding-bottom: calc(16rpx + env(safe-area-inset-bottom))`。
- 内容末尾必须留出**与固定栏等高的占位**（`purchase/detail` 的 `.action-spacer`），不能只放 `ios-safe-bottom`。
- 自定义导航页统一用 `utils/nav.js` 的 `getNavTopOffset()`，按胶囊实际位置下移，不写死状态栏高度。

### 10.4 滚动

- `scroll-view` 必须显式高度，且 `:enhanced="true" :bounces="false"`，避免内层滚动带动页面下拉刷新。
- 横向筛选条外层 `white-space: nowrap` + 内层 `inline-flex`，否则 chip 会竖排。
- 列表右侧数值列 `flex-shrink: 0`，标题列 `min-width: 0` + 省略号，防止长名称把金额挤换行。
- `scroll-into-view` 的目标 id 唯一时直接赋值，不要「先清空再赋值」，会抖动。

### 10.5 文本与对比度

- 正文 28~32rpx，次要信息 26rpx，时间/单位 22~24rpx；单行过长一律 `ios-ellipsis`。
- 次要文字用 `rgba(60,60,67,.6)`；空状态不要用 `.3` 的极浅灰，改用 `.6` 保证可读。
- 数字用等宽或固定宽度对齐，金额统一两位小数。
