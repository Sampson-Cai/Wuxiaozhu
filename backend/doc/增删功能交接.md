# 增删功能交接

> 面向负责"增 + 删"的同学。改查部分（列表、详情、编辑、状态流转）已由另一位同学完成，本文只讲新增与删除。
> 接口前缀 `/business`，返回 `{code,msg,...}`，写接口**必须**带 `X-Request-Id`。

## 1. 已有的增删接口

### 增

| 功能 | 接口 | 控制器方法 | 服务 / Mapper | 表 |

| 入库 | `POST /business/stock/inbound` | `AppStockController.inbound` | `StockServiceImpl.inbound` → 首次 `insertStock`，之后 `addStockQty` + `insertRecord` | `t_stock` / `t_stock_record` |

### 删

| 功能 | 接口 | 控制器方法 | 规则 | 表 |
| --- | --- | --- | --- | --- |
| 商品分类 | `DELETE /business/category/{id}` | `AppCategoryController.remove` | 有子分类或商品时拒绝；逻辑删 `del_flag='2'` | `t_product_category` |
| 商品 | `DELETE /business/product/{id}` | `AppProductController.remove` | 逻辑删，**暂无引用校验** | `t_product` |
| 供应商 | `DELETE /business/supplier/{id}` | `AppSupplierController.remove` | 逻辑删，**暂无引用校验** | `t_supplier` |

> 其余实体没有删除接口，这是设计选择：采购单用"取消"、库存流水/付款记录不可删、补货参数用 `enableFlag` 停用、账号用"停用"。

## 2. 待补的四个功能

### 2.1 采购单删除（草稿作废）——优先

**为什么**：前端"删除草稿"按钮没接口，现在只能取消，取消后单据还留在列表里。

**接口设计**

```
DELETE /business/purchase/{orderId}
权限：business:purchase:edit
```

**改哪里**

1. `AppPurchaseController` 增加 `remove(@PathVariable Long orderId)`，取 `enterpriseId()`，调 service，返回 `AppResult.ok("删除成功")`；
2. `IPurchaseService` + `PurchaseServiceImpl` 增加 `delete(Long enterpriseId, Long orderId)`：
   - `requireOrder` 校验存在；
   - `status` 必须是 `0`（草稿），否则抛 `ServiceException("仅草稿可以删除")`；
   - 调 `purchaseOrderMapper.deleteOrder(enterpriseId, orderId)`，影响行数为 0 时抛"状态已变化"；
3. `PurchaseOrderMapper` + XML 增加：

```xml
<update id="deleteOrder">
    update t_purchase_order set del_flag = '2', update_time = sysdate()
    where enterprise_id = #{enterpriseId} and order_id = #{orderId} and status = '0'
</update>
```

明细不用删，列表和详情都按主单过滤。

**验收**：草稿删掉后列表查不到、详情返回"采购单不存在"；待审批/已通过调用返回"仅草稿可以删除"。

### 2.2 商品删除前校验引用

**为什么**：被采购单引用的商品现在能删，删完采购明细里的商品选择器就找不到它了。

**改哪里**

1. `ProductMapper` + XML 增加两个计数：

```xml
<select id="countPurchaseItems" resultType="int">
    select count(1) from t_purchase_order_item i
    inner join t_purchase_order o on o.order_id = i.order_id
    where i.product_id = #{productId} and o.enterprise_id = #{enterpriseId} and o.del_flag = '0'
</select>
```

2. `AppProductController.remove` 删除前：

```java
if (productMapper.countPurchaseItems(eid, productId) > 0) {
    return AppResult.error("该商品已被采购单引用，建议改为停用");
}
Stock stock = stockMapper.selectStockByProduct(eid, productId);
if (stock != null && stock.getQty() != null && stock.getQty().compareTo(BigDecimal.ZERO) > 0) {
    return AppResult.error("该商品仍有库存，请先出库或改为停用");
}
```

3. 停用接口已存在：`PUT /business/product/{id}/status?status=1`，提示语里引导用户用它。

**验收**：被引用/有库存的商品删除返回提示，停用成功；无引用的商品删除后列表消失、历史单据明细仍能显示快照名称。

### 2.3 供应商删除前校验引用

**改哪里**

1. `SupplierMapper` + XML：

```xml
<select id="countOrders" resultType="int">
    select count(1) from t_purchase_order
    where supplier_id = #{supplierId} and enterprise_id = #{enterpriseId} and del_flag = '0'
</select>

<select id="countUnpaid" resultType="int">
    select count(1) from t_payable
    where supplier_id = #{supplierId} and enterprise_id = #{enterpriseId} and status != '2'
</select>
```

2. `AppSupplierController.remove`：有单据或未结清应付 → 拒绝，提示"请先处理应付账款或改为停用"。

**验收**：有应付的供应商删不掉；停用后新采购单选不到它。

### 2.4 新增账号

**为什么**：小程序端不能建账号，只能去后台网页；单位管理员在手机上没法加人。

**接口设计**

```
POST /business/user
权限：business:user:edit
Body: { "loginName","userName","password","phonenumber","email","deptId","roleIds":[101] }
```

**改哪里**

1. `AppUserController` 增加 `add(@RequestBody SysUser user)`；
2. 校验：`userService.checkLoginNameUnique(user)`、`checkPhoneUnique`、密码长度 ≥ 6；
3. 单位与会话信息由服务端注入：

```java
user.setEnterpriseId(eid);
user.setSalt(ShiroUtils.randomSalt());
user.setPassword(passwordService.encryptPassword(user.getLoginName(), user.getPassword(), user.getSalt()));
user.setPwdUpdateDate(DateUtils.getNowDate());
user.setCreateBy(operator());
userService.insertUser(user);   // 内部会写 sys_user_role
```

4. 参考实现：`SysUserController.addSave`（第 132–153 行），口令加密方式一致，否则新账号登录不了；
5. 返回 `AppResult.ok("新增成功").put("userId", user.getUserId())`。

**验收**：新账号能登录、`/getInfo` 返回其角色权限、`/business/user/list` 只看到本单位用户。

> 账号"删除"不做：用已有的 `PUT /business/user/{id}/status?status=1` 停用即可，避免历史单据的操作人丢失。

## 3. 写代码时必须遵守的约定

| 项 | 约定 |
| --- | --- |
| 幂等键 | 写接口必须带 `X-Request-Id`，否则 500；重复返回 409 |
| 单位隔离 | 从 `enterpriseId()` 取，禁止接收前端传的 `enterpriseId` |
| 删除方式 | 一律逻辑删 `del_flag='2'`，不物理删 |
| 状态并发 | 改状态用条件 UPDATE（`where status = ?`），影响行数 0 就抛异常 |
| 权限点 | 写操作加 `@AppPermission("business:xxx:edit")`；新权限点同步 `sql/cangxiaozhu_menu.sql` |
| 审计 | 不用手动写，拦截器已自动落 `sys_oper_log` |
| 事务 | Service 写方法加 `@Transactional(rollbackFor = Exception.class)` |
| 校验 | 必填、长度、唯一性在 Controller 校验；业务规则在 Service |

## 4. 本地验证

```bash
# 启动（关验证码便于脚本）
java -jar ruoyi-admin/target/ruoyi-admin.jar --server.port=18080 --shiro.user.captchaEnabled=false

# 登录拿 token
TOKEN=$(curl -s -X POST http://127.0.0.1:18080/login \
  -d "username=admin&password=admin123" | sed 's/.*"token":"\([^"]*\)".*/\1/')

# 示例：删除草稿（记得带 X-Request-Id）
curl -X DELETE http://127.0.0.1:18080/business/purchase/1 \
  -H "Authorization: Bearer $TOKEN" -H "X-Request-Id: test-del-001"
```

验证失败分支时换个 `X-Request-Id`，否则会命中幂等记录返回 409。
